# Запуск zotov.kz и передача инфраструктуры Саше

Проверено 12 октября 2026 года. Пользователь купил zotov.kz на Hoster.kz,
создал хостинг с корневой папкой httpdocs и установил Sectigo PositiveSSL.
Публичный HTTPS отвечает без ошибки сертификата; HTTP и www перенаправляются
на https://zotov.kz/ с кодом 301. Сайт опубликован на Hoster.kz;
настройки в панели пользователь меняет самостоятельно.

Все проверки выполняются локально перед каждым пушем в `main`/`master` и PR merge:
`bun run hooks:install` один раз на клон, затем полный `release:check` с production
переменными. GitHub Actions удалены; автоматическая публикация не используется.
Актуальный состав проверок и ограничения hook: [локальные проверки](local-checks.md).

## Рекомендуемая схема

| Что | Где | Владелец |
| --- | --- | --- |
| Регистрация и продление zotov.kz | Hoster.kz | Саша / бизнес |
| Основной сайт | Хостинг на сервере в Казахстане, например Hoster.kz | Саша / бизнес |
| DNS основного сайта | Hoster.kz | Саша / бизнес |
| Cloudflare DNS, если понадобится позднее | Аккаунт Cloudflare Саши, режим DNS only для сайта | Саша |
| Технический предпросмотр, если нужен | Отдельный Cloudflare Pages проект | Саша |
| Исходники | GitHub-репозиторий с доступом владельца и разработчика | Согласовать владельца |

Регистратор, DNS и хостинг — разные услуги. Домен может оставаться купленным
на Hoster.kz, а DNS обслуживаться Cloudflare. Переносить регистрацию домена
в Cloudflare для этого не требуется.

**Поправка к первоначальному плану:** Cloudflare Pages не выбран хостингом
основного `.kz`-сайта. По [разъяснению KazNIC](https://www.nic.kz/docs/reminder_domain_violation.pdf)
веб-ресурс должен размещаться на сервере в Казахстане; зарубежные DNS разрешены.
Проксирование зарубежного хостинга не заменяет размещение в Казахстане.
Для исходной настройки используем DNS Hoster.kz; HTTPS обеспечивает хостинг.
Cloudflare DNS остаётся отдельным вариантом, без необходимости переноса сейчас.
Включение Cloudflare proxy потребует отдельного
согласования условий с регистратором и подтверждения казахстанского хостинга.

## 1. Покупка и права доступа

1. Создать личный кабинет Hoster.kz на Сашу / бизнес. Указать реального владельца
   домена и его контактный адрес. Купить `zotov.kz` там сразу, чтобы потом
   не переоформлять регистрацию.
2. Выбрать хостинг для статического сайта с сервером в Казахстане, HTTPS,
   поддержкой 404 и перенаправлений. Для этой Astro-сборки Node.js на сервере
   не нужен: публикуются готовые файлы `website/dist`.
3. Саша создаёт свой Cloudflare-аккаунт и при необходимости приглашает разработчика
   с доступом к нужной зоне. Личные пароли не передаются.
4. Если домен уже куплен в другом кабинете Hoster.kz, смена NS не передаёт
   владение доменом. Потребуется отдельное
   [переоформление и перенос услуги](https://hoster.kz/support/personal-area/8439/).

## 2. Запуск основного сайта на казахстанском хостинге

1. Добавить домен и `www.zotov.kz` в панели хостинга. Получить IP сервера,
   каталог сайта и способ загрузки файлов. Уточнить расположение сервера.
2. Выбрать один вариант DNS:
   - **Проще:** оставить NS Hoster.kz и управлять записями через его
     [DNS-хостинг](https://hoster.kz/support/upravlenie-dns-zapisyami-domenov/5537/).
   - **С Cloudflare Саши:** добавить `zotov.kz` в его аккаунт, создать A-запись
     `@` на IP хостинга и запись `www` на этот же хостинг. Для веб-записей выбрать
     DNS only. В Hoster.kz заменить серверы имён домена на пару NS, выданную
     Cloudflare именно для аккаунта Саши. Не использовать NS из старого аккаунта.
     Это смена делегирования у регистратора, а не добавление обычной NS-записи
     в таблицу DNS. Если используется почта, сохранить MX/TXT и остальные записи.
3. Выпустить действующий HTTPS-сертификат для основного домена и www. Настроить
   HTTP → HTTPS и www → основной домен с кодом 301, сохраняя путь и query.
4. Перед выпуском исправить выявленные уязвимости зависимостей и выполнить:

   ```bash
   PUBLIC_WEBSITE_URL=https://zotov.kz PUBLIC_ALLOW_INDEXING=true bun run release:check
   ```

   Проверить main, remote и чистое рабочее дерево. Эти параметры задаются
   **до сборки**: замена файлов DNS не меняет canonical и noindex в готовом HTML.
5. Загрузить содержимое `website/dist` в каталог сайта после успешных проверок
   и разрешения на публикацию. Не копировать исходники или node_modules.
   Сначала сохранить предыдущую версию для отката.
6. Настроить на выбранном сервере корректную отдачу `/privacy/`, 404 для
   неизвестных путей, сжатие HTML/CSS/JS и кеширование статических ресурсов.
   `website/public/_headers` — формат Cloudflare Pages: Hoster.kz не обязан
   применять этот файл. Заголовки CSP/безопасности и кеша нужно проверить
   и при необходимости перенести в конфигурацию веб-сервера.

Скрипт `bun run cf:deploy` публикует в Cloudflare Pages, поэтому для основного
сайта на Hoster.kz его не используем. Автоматизацию доставки файлов на Hoster.kz
подготовим отдельно, когда известны панель и способ доступа; защиты release:check
должны сохраниться. До запуска технические сборки остаются indexing=false.

### Первый запуск через ZIP в Plesk

Для нового production-архива из корня репозитория выполните `bun run deploy:archive`.
Команда запускает полный `release:check` с доменом `https://zotov.kz`, индексацией
и GA4 `G-CJVPRBC0P6`, проверяет согласия, затем создаёт
`artifacts/deploy/zotov-kz-<дата-время-UTC>-<commit>[-dirty].zip` и JSON с параметрами
и контрольными суммами. Яндекс Метрика отключена. Существующие ZIP сохраняются;
новый архив готов к ручной загрузке и не публикуется автоматически.

Архив первого запуска: `artifacts/deploy/zotov-kz-production.zip`. Предыдущий
`zotov-kz-preview.zip` закрыт от поисковиков и не подходит для финального запуска.
Собирать production с `PUBLIC_WEBSITE_URL=https://zotov.kz` и
`PUBLIC_ALLOW_INDEXING=true` только после успешного `release:check`.

Архив содержит файлы сборки в корне, а не папку dist. Из отдельной временной
копии сборки исключаются `_headers` и `_redirects`; туда копируется
`scripts/deploy/hoster.htaccess` как `.htaccess`. Generated dist не редактируется.
В ZIP не должны попасть исходники, node_modules, `.env`, ключи и сертификаты.

1. Сохранить резервную копию всего httpdocs и убрать её из публичной папки.
2. В «Хостинг и DNS → Apache и nginx» оставить Proxy mode включённым;
   отключить Smart static files processing и Serve static files directly by nginx.
   Иначе nginx может обойти заголовки и 404 из `.htaccess`. Если этих настроек
   нет в тарифе, попросить поддержку Hoster передать запросы в Apache.
3. Через «Файлы» загрузить новый проверенный ZIP в httpdocs и распаковать туда же с заменой
   index.html. Не удалять существующие cgi-bin и bitrixsetup.php.
4. Проверить, что index.html, _astro, fonts, privacy и .htaccess лежат прямо
   в httpdocs. Удалить ZIP из публичного каталога после распаковки.
5. Проверить главную, /privacy/, неизвестный URL (HTTP 404), мобильное меню,
   WhatsApp и телефон, картинки, шрифты, CSP и остальные заголовки, кеширование
   и сжатие. Проверить robots.txt, sitemap.xml, canonical и отсутствие noindex
   на индексируемых страницах. Настройку HTTPS/301 в Plesk сохранить.
6. При ошибке восстановления вернуть резервную копию файлов и исходные
   настройки Apache/nginx; повторную публикацию сделать после исправления.

`minimumReleaseAge` остаётся 21 день. Исключения в bunfig.toml относятся к
исправлениям security-аудита и их обязательным платформенным библиотекам.
Пересмотреть исключения после выдержки этих версий; новые пакеты не должны
добавляться в список без конкретной причины. Типы Node.js нужны только для
чистой проверки Astro и находятся в devDependencies.

## 3. Как передать Cloudflare Pages из моего аккаунта в аккаунт Саши

Практический путь — создать новый проект в аккаунте Саши и развернуть там
сайт из репозитория. Историю развёртываний и настройки старого проекта не
считаем автоматически перенесёнными. Это отдельная задача от регистрации `.kz`.

### Вариант А: сохранить старый сайт во время передачи

Для технического предпросмотра создать у Саши проект **Direct Upload**,
загрузить туда проверенную сборку с `PUBLIC_ALLOW_INDEXING=false` и новым
техническим URL. Старый Pages-проект пока остаётся доступным. GitHub-репозиторий
может оставаться у текущего владельца: его передача — отдельное решение.

Для последующих публикаций использовать права и Account ID Саши. Если имя
проекта отличается, обновить `wrangler.jsonc` перед использованием штатного
скрипта публикации. Токены хранить вне репозитория; старый токен не переносить.
В Direct Upload проект позже нельзя подключить встроенную Git integration.
Текущая политика предусматривает локальные проверки и отдельно разрешённую
ручную публикацию; отдельный CI не подключается.
[Документация Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/).

### Вариант Б: сохранить встроенные сборки Pages из GitHub

Этот прежний вариант не используется при текущей политике локальных проверок
и ручной публикации. Его подключение требует отдельного изменения политики.

Cloudflare [запрещает подключать один GitHub/GitLab-репозиторий к Pages в разных аккаунтах](https://developers.cloudflare.com/pages/configuration/git-integration/troubleshooting/).
Поэтому новый Git-проект с тем же репозиторием нельзя считать способом
параллельного переноса без остановки старого проекта.

Возможны два пути:

- Сначала использовать вариант А, проверить новый сайт, сохранить старую
  конфигурацию, а затем отдельно согласовать удаление старых Pages-проектов,
  использующих репозиторий, и подключение репозитория к новому Git-проекту Саши.
  Старый pages.dev-адрес при удалении проекта перестанет обслуживаться; историю
  развёртываний и сохранение того же адреса не обещаем.
- Создать отдельный репозиторий для Саши и подключить его к новому Git-проекту.
  Старый сайт продолжит работать, но нужно определить, какой репозиторий
  основной, и перенести историю/права отдельно. Одной выдачи доступа Саше
  к существующему репозиторию недостаточно, чтобы обойти ограничение Cloudflare.

Будущие настройки Git-проекта для этого Bun workspace:

| Настройка | Значение |
| --- | --- |
| Production branch | main |
| Root directory | Корень репозитория, не website |
| Build command | bun run build |
| Build output directory | website/dist |
| Bun | Версия из .bun-version, сейчас 1.3.14 |
| PUBLIC_WEBSITE_URL | Реальный технический URL нового проекта |
| PUBLIC_ALLOW_INDEXING | false в production и preview технического проекта |

Проверить совместимость версии build image с Bun и применение build-time
переменных; значения `wrangler.jsonc` должны соответствовать выбранному проекту.
Подключение GitHub и создание проекта может запустить сборку/публикацию.
[Настройки Git integration](https://developers.cloudflare.com/pages/get-started/git-integration/).

### Если доменная зона уже заведена в моём Cloudflare

Если домен ещё не куплен/не подключён, завести его сразу у Саши — перенос зоны
не нужен. Если зона уже есть: экспортировать DNS, добавить её у Саши,
восстановить записи и правила, затем заменить NS в Hoster.kz на новые.
При включённом DNSSEC сначала корректно удалить старую DS-запись у регистратора,
после активации новой зоны включить DNSSEC заново с новыми данными.
Не удалять старую зону до проверки переключения. Настройки и account-level
правила не считать перенесёнными вместе с DNS.
[Перенос зоны между аккаунтами](https://developers.cloudflare.com/fundamentals/manage-domains/move-domain/).

Если впоследствии для другого подходящего домена выбирается именно Pages,
для корневого домена зона DNS и Pages-проект должны быть в одном аккаунте.
[Требования к custom domains](https://developers.cloudflare.com/pages/configuration/custom-domains/).

## 4. Старый адрес и проверка запуска

Старый `zotov-landing.pages.dev` относится к текущему проекту. Если он нужен
для постоянного 301 на `https://zotov.kz`, сохранить старый проект
и настроить точный Bulk Redirect в **старом аккаунте** после готовности сайта.
Новый аккаунт Саши не управляет этим старым адресом. Не включать Include subdomains:
preview-адреса должны оставаться доступны и закрыты от индексации.
[Редирект pages.dev](https://developers.cloudflare.com/pages/how-to/redirect-to-custom-domain/).

Перед завершением передачи проверить:

- HTTPS на основном домене и www; перенаправления сохраняют путь и query.
- canonical, og:url и JSON-LD указывают на `https://zotov.kz`.
- Production: нет noindex/X-Robots-Tag noindex; robots разрешает обход;
  sitemap содержит только опубликованные адреса. Предпросмотр: noindex.
- `/privacy/` открывается; неизвестный путь отдаёт 404; WhatsApp, телефон,
  меню и карусели работают; заголовки безопасности и кеша применены хостингом.
- Проверки desktop/mobile и Lighthouse выполнены на опубликованном сайте.
- При наличии доступа домен подтверждён в Search Console и отправлен sitemap.
- Саша управляет продлением домена и хостинга, DNS, исходниками и доступами;
  лишние доступы и старые токены отозваны после проверки.

Ничего не удаляем и не переключаем в действующих аккаунтах на основании этой
инструкции автоматически. Покупка, публикация и переключение DNS — отдельные
согласованные действия.
